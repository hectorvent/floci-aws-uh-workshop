  • The loop: plan, act, observe, repeat
    • 
      
  • An agent is only as good as the errors it gets back
    •

    •

S3 tells SQS about every new file

  

resource "aws_s3_bucket" "uploads" {
  bucket = "uploads"
}

resource "aws_sqs_queue" "events" {
  name = "uploads-events"
}

resource "aws_s3_bucket_notification" "to_queue" {
  bucket = aws_s3_bucket.uploads.id

  queue {
    queue_arn = aws_sqs_queue.events.arn
    events    = ["s3:ObjectCreated:*"]
  }
}
  

  
References like aws_sqs_queue.events.arn are the arrows: Terraform creates things in that order.

  

    Last step highlights lines 10 and 13: the notification references the bucket and the queue. That reference is the arrow in the diagram.
    In main.tf the notification also has depends_on = [aws_sqs_queue_policy.allow_s3]. The queue policy (not shown) allows s3.amazonaws.com to send to the queue. Real AWS rejects the notification without it;
    Floci 2.5.0 accepts it, which is one of the gaps on the limits slide at the end.
  






  
SQS triggers the Lambda

  

resource "aws_lambda_function" "process_upload" {
  function_name = "process-upload"
  role          = aws_iam_role.lambda.arn
  runtime       = "python3.12"
  handler       = "handler.handler"
  filename      = data.archive_file.lambda.output_path
  timeout       = 10
}

# Poll the queue and call the function for every message
resource "aws_lambda_event_source_mapping" "from_queue" {
  event_source_arn = aws_sqs_queue.events.arn
  function_name    = aws_lambda_function.process_upload.arn
  batch_size       = 1
}
  

  
Simplified for the slide. The full file also zips src/handler.py and defines the IAM role.

  

    Line 3: the function runs as the IAM role, which only allows reading this queue and writing logs.
    Lines 12-13: the event source mapping is the "trigger" arrow. Floci runs the function in a real
    python3.12 Lambda container, which is why Lab 0 needs Docker.
  






  
The code the Lambda runs: src/handler.py

  

import json

def handler(event, context):
    for record in event["Records"]:           # one SQS message
        body = json.loads(record["body"])     # the S3 event inside it
        for s3_event in body.get("Records", []):
            bucket = s3_event["s3"]["bucket"]["name"]
            key = s3_event["s3"]["object"]["key"]
            size = s3_event["s3"]["object"].get("size", 0)
            print(f"PROCESSED s3://{bucket}/{key} ({size} bytes)")
    return {"ok": True}
  

  
That PROCESSED line lands in CloudWatch Logs. verify.sh waits for it.

  

    An S3 event wrapped inside an SQS message: the handler unwraps two layers.
    Remember line 5 (record["body"], lowercase). Lab 3 breaks it, and the agent has to find it in the logs.
    Don't say that out loud yet.

What an emulator can't tell you

  

    

      
Accepted by Floci 2.5.0, rejected by AWS

      
    
        
  • S3 → SQS notification when the queue policy doesn't let S3 send
    • 
        
  • Event source mapping with queue visibility timeout < function timeout
    • 
        
  • Lambda function with an IAM role that doesn't exist
    • 
      

    

    

      
Hard to emulate at all

      
    
        
  • IAM policy evaluation edge cases
    • 
        
  • Service quotas and limits
    • 
        
  • Real latency, throttling, eventual consistency
    • 
        
  • Newer or less common features
    • 
      

    

  

  
Pass locally, then validate in a real sandbox account before production.

  

    All three on the left were re-tested on Floci 2.5.0 (2026-11-16) and are still accepted. Contrast: Floci does reject a notification to a queue
    that doesn't exist (Lab 3's first bug) and an EKS cluster with a subnet that doesn't exist.
    An agent that passes locally and breaks prod is worse than one that never ran.
    Story beat: Alex's professor asks, "Will it work on real AWS?" This slide is Alex's honest answer.
    One more gap found while timing Lab 2 (Floci 2.5.0): Floci lets you re-create an SQS queue with the same name right

Floci 2.5.0 on a laptop, images already pulled. *AWS: terraform destroy (≥45 s) + 60 s before SQS lets you reuse the queue name + apply. Floci: floci aws reset (~1 s) + apply (57 s, mostly Terraform's own waits).

  

    Real-cloud sources (verify before presenting): AWS EKS announcement (control plane in about 9 minutes on average),
    a Terraform timing benchmark (EKS 11m19s create, 8m18s destroy, 30+ min round trip), RDS provider docs
    (5 to 7 min for MySQL/PostgreSQL, longer for SQL Server).
    Floci times re-measured on 2.5.0 (2026-11-16), polling every 0.5 s: EKS create → ACTIVE 11–14 s (was 7–9 s on 2.4.0),
    delete ~1.1 s; RDS PostgreSQL create → available 2–3 s; create-vpc 0.46 s (a plain AWS CLI call is ~0.4 s);
    Lab 2 apply 62 s; server start ~55 ms on restart (150–550 ms on a first start).
    Don't use "aws eks wait cluster-active" to demo this: it polls every 30 s and makes Floci look like 31 s.
    Lab 2 row is the loop the agent runs in Lab 3 ("destroy everything and rebuild"), not a single first apply.
    A single apply is ~1 min on both, because Terraform AWS provider v5.100.0 itself waits: it re-reads a new SQS queue
    and queue policy 6 times, 5 s apart (sqs/queue.go). The loop is where AWS loses time:
    destroy waits for the deleted queue to read as gone 15 times, 3 s apart (>=45 s, waitQueueDeleted);
    AWS then refuses a queue with the same name for 60 s (QueueDeletedRecently, documented on DeleteQueue);
    then the apply again (~1-1.5 min with IAM propagation retries). About 3 min, estimated, not measured.
    Floci measured on 2.5.0: floci aws reset 0.4 s + apply 57 s. Over the 12 attempts of Alex's night: ~36 min vs ~12 min.
    To replace the estimate, time one destroy + apply in a real sandbox account.
    Total row: EKS create + destroy (9-15 min + ~8 min) + RDS (5-15 min) + VPC (seconds) + Lab 2 loop (~3 min) = ~25-40 min.
    Floci: 12 s + 1 s + 3 s + <1 s + 57 s + 0.4 s reset = ~75 s. Startup left out (tens of ms, no AWS equivalent).
    Line to say: "Half an hour on AWS, about a minute on Floci. And the agent does it again on every attempt."
